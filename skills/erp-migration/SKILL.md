# 旧 ERP 业务域迁移

新系统在本仓（Java + Vue），旧系统在同级 `../oldErp/`：主站 `erp_code/modules/`、美国站 `erp_us_code/modules/`。

**一个业务域 = 一条完整单据链**（采购：请购→采购单→到货→质检→入库→结算）。产出是方案与清单，不是代码。

## 第一步：先定模块

旧仓不是单应用，是**每模块一个独立应用**。所有取证路径都要带模块前缀，否则找不到文件。

1. 候选模块查 `<TOOLS_DIR>/skills/erp-migration/references/old-erp-map.md`（主站 21 个 / 美国站 14 个，含各模块框架与目录形态）
2. 一个业务域常横跨多个后端模块（例：在线库存同步 = `erp_storage` + `erp_product` + `erp_order`），**必须列全**；只读一个必然漏功能
3. 业务页面不在后端模块里：主要在 `modules/erp_html/app/pages/<域>/`（React），其他前端模块各自 `src/`（Vue/TS）
4. 模块清单写进说明书 §1，之后每条证据都带模块前缀

## 前置检查（没说清就问，不猜）

1. **域与单据范围**——包含哪些单据，边界在哪
2. **站点**——主站 / 美国站。默认主站；美国站差异另出「分叉清单」，不混进主说明书
3. **目标新模块**——`hexin-modules/{oms,wms,masterdata,pda,workflow,openapi}`
4. **报表是否单独排期**——默认单独；本说明书只列报表清单与 SQL 出处，不拆口径
5. **新系统该域现状**——已实现 / 部分实现 / 空。**读代码判断**：后端 `hexin-modules/<m>/src/main/java`，前端 `Hexin_ui/src/views/<域>/`；不看模块名猜

域过大（一次读不完、画不出完整 DAG）→ 先出拆分方案让用户确认，再逐子域做。

## 取证来源

漏功能都漏在这几处。逐类核对，每类在覆盖矩阵里至少留一行：

| 来源 | 位置（模块内） | 要拿到什么 |
|---|---|---|
| 页面与接口 | `app/Http/Controllers` + `routes/web.php`、`routes/api.php` | 全部入口，含菜单没有、直连 URL 能访问的 |
| **数据权限** | `app/Scopes` + 控制器里的 `byDataPermission` | 每个角色能看到哪些数据——重写最容易整块丢。只有部分模块有 Scopes |
| 定时任务与队列 | `app/Console/Commands` + `app/Jobs` | 任务清单、频次、是否幂等 |
| 导入导出 | `app/Imports` + `app/Exports` | 模板列与格式（对外承诺，不能随手改） |
| 校验规则 | `app/Rules` + FormRequest | 业务约束 |
| 库表与权限点 | 菜单表、权限点表（连库查） | 反推功能点；代码里搜不到 |
| 报表口径 | `modules/erp_olap/**/*.sql` | 指标定义只写在这里。SQL 可能跑在 ClickHouse/Doris，不是 MySQL |
| 前端页面 | `modules/erp_html/app/pages/<域>/`；其他前端模块 `src/` | 批量操作、默认值、联动、表格列 |
| 打印/导出模板 | `resources/views/{export,tool,mobile_tool}.blade.php` | 打印版式与导出字段 |

`resources/views` 不是业务页面所在，别在那里找页面。

## 连库取证

旧系统每模块一套连接：`config/database.php` 有 mysql / pgsql / mongodb / clickhouse 四种，业务主库按域分库（如 `hexin_storage`）。

- 连接信息在各模块目录下的 `测试环境.env`（只有部分模块带此文件）；**账号密码不进文档**
- 查库走 db-access，先跟用户确认连哪个实例
- **美国站模块的库名可能与主站同名**（`us_wms_hexin_storage` 的 `DB_DATABASE` 也是 `hexin_storage`），连之前必须确认实例，不能按库名判站点
- 连不上就要用户给导出或截图，**数字标来源与日期，不猜**

## 执行：8 节说明书

按顺序做。第 2 节的覆盖矩阵是核心交付物，不是附录。

1. **域边界与交接**——模块清单、角色、单据、域内域外分界；往上下游交什么、由谁接
2. **功能取证与覆盖矩阵**——上表逐类穷举，每条落到矩阵一行
3. **实体、状态机与流程闭环**——每张表字段、状态枚举、迁移触发者；正向主流程 + 逆向（退回/取消/冲销）+ 异常分支（部分到货、超收、质检不合格、拆合单）
4. **上下游数据关联**——单据 DAG + 字段血缘（来源单据字段 → 本单据 → 去向）
5. **规则清单**——校验、编码、单位换算与精度、权限点、审批流、库存占用；**并发、事务边界、幂等**单独标
6. **PHP→Java 语义差异风险**——这些改了不报错、只会算错：
   - 弱类型比较（`"1" == 1`）、空值判定（`"0"` / `""` / `null` 皆假）
   - 金额与数量精度：PHP float → Java `BigDecimal`，舍入规则定死
   - 关联数组缺字段时的默认值 → Java DTO 报错或丢数据
   - 事务边界：请求级短事务 → Spring 事务，库存扣减与单号生成会出新问题
   - 跑批幂等：老 cron 多半不幂等，搬到定时任务/MQ 后重试会重复执行
7. **合理性评估**——逐条判 **A 照搬 / B 改造 / C 不复用 / D 废弃或合并**，每条写理由。D 档附证据（入口是否还在、近一年数据量、操作日志、是否被下游或报表引用）
8. **数据影响与基础数据**——只出意见，不设计迁移：
   - 历史单据怎么查（旧系统只读期）、跨期报表口径断点、单号是否冲突、旧系统何时下线
   - **基础数据前置清单**：本域用到哪些仓库/库位/商品/供应商/单位/字典，新系统有没有，缺的谁补
   - **存量是否定时同步**（见下节）
   - 报表与指标清单（含 SQL 出处），交单独排期

## 旧实现自相矛盾（固定小节）

旧仓常有「页面算一套、Job 算一套」。比废弃更危险：搬错一套，金额和库存会长期错。

- 在 §7 后单列一节，逐条写：**矛盾点、两套行为各在哪、UAT 实际跑的是哪套、新系统取哪套及理由**
- 重点查三对：列表与推送、页面校验与后端校验、文案与实现
- 样例见 `<TOOLS_DIR>/skills/erp-migration/references/deliverable-templates.md`

## 数据同步结论（四选一）

先连库取证，不凭表名猜：

| 取证 | 看什么 |
| --- | --- |
| 数据量 | 实际行数、`information_schema` 的 `data_length + index_length` |
| 时间水位 | 保存/导入是否写 `update_time`，列有没有 `ON UPDATE`。有一处不写，水位就不可靠 |
| 写入方 | 过渡期旧页面还改不改。还在改，过渡期以旧库为准 |
| 切流 | 重构页面开始维护后必须停止从旧库覆盖，否则新改的值会被盖掉 |

结论只能是：**不迁** / **一次性搬入，切流前再整表覆盖一次** / **定时全量覆盖**（切流后停任务）/ **定时增量**（仅当所有写入路径都推进更新时间）。禁止按不可靠的 `update_time` 做增量。新页面能按主数据现查出来的空骨架行不必同步。

## 交付物

全部放本仓 `docs/migration/<域>/`，模板与状态取值见 `<TOOLS_DIR>/skills/erp-migration/references/deliverable-templates.md`：

- `<域>-迁移说明书.md`——8 节 + 矛盾小节。给实现用
- `<域>-覆盖矩阵.md`——行=功能点（带取证来源），列=新系统状态 + 证据，要能算覆盖率
- `<域>-废弃清单.md`——D 档逐条，含证据、影响面、建议处置
- `<域>-功能说明.md`——给汇报和转述，口径收口后生成，不等功能实现；子域拆分时每个子域一份
- 拆成多个子域时加 `README.md`：子域清单与状态（待做/进行中/已完成），跨会话靠它续跑

功能说明写作用、能做什么、流程图、数据上下游怎么流转；不写取证路径、覆盖率和实现任务。生成时机与骨架见模板。

## 说明书必写

缺任一项不算完成：

1. **功能在项目中的作用**——谁用、上游交来什么、下游谁读。写在第 1 节，不只有菜单名
2. **旧项目表**——`库.表`，每张表一行：存什么、谁写入。主数据与本功能专属字段分开
3. **重构项目表**——已有写 `库.表`；没有写「尚无」并给拟落表。不要把「主数据已在」写成「这个功能的数据已在」
4. **同步结论**——按上节四选一，附数据量、时间水位、过渡期写入方、切流后是否停任务

## 证据纪律

- 每条结论带出处：`modules/<模块>/<路径>:行号` 或 `库.表.字段`。金额、状态迁移、库存数量三类必须精确到方法
- 找不到证据标「待确认」，不推断
- 区分「旧系统实际行为」与「旧系统本意」，不一致时写进矛盾小节
- 判定新系统现状前必须先读新代码

## 废弃门禁

D 档在用户确认前一律按「必须实现」处理。

- 生成废弃清单后**停下**，逐条请用户确认，不推进实现
- 涉及外部对接、财务结算、审计留痕的，即使低频也先保留
- 未确认项在矩阵里保持「待确认」，不写「废弃」

## 口径收口与功能说明

功能说明只在口径收口后写，不等功能实现。

1. 矩阵里的 `待确认` 逐条请用户定论：给结论，或转「本期不做」由用户确认并回写。收口后头部待确认条数必须为 0
2. 废弃清单逐条回写用户结论；矛盾小节写定新系统取哪套
3. 两项完成后生成 `<域>-功能说明.md`，它是本次方案交付的一部分，缺了不算结束
4. 实现之后代码与已确认口径不一致，改代码；只有用户重新确认口径才改功能说明

## 验收

实现完成后按矩阵逐行核对：

- 每行状态落到 **已有** 或 **本期不做（已确认）**，不接受「差不多」
- 覆盖率 = 已有且行为符合 / 本期要做，写在矩阵头部
- §3 的逆向与异常分支逐个用例验证，不只跑主流程
- 同步结论里的一次性/定时任务，验证跑过且数据对得上

## 停止线

只出方案与清单，不写业务代码。结束时给**实现任务清单**：每条对应覆盖矩阵的一行或一组行，写明工作区、分支、基线；末尾一句「要开始实现说一声」。实现阶段走 git-workflow。

## 失败处理

| 情况 | 动作 |
|---|---|
| 域名对不上模块 | 查 `<TOOLS_DIR>/skills/erp-migration/references/old-erp-map.md` 列候选让用户选，不硬猜 |
| 域跨多个模块 | 全列进 §1 逐个读；没读完的标「待确认」 |
| 新旧找不到对应 | 进第 8 节，不中断 |
| 功能点无法判断是否在用 | 标「待确认」，进废弃清单让用户定 |
| 旧库连不上 | 要用户给导出/截图，数字标来源日期，不猜 |
| 报表口径找不到文档 | 以 `erp_olap` 里的 SQL 为准，标文件路径 |
| 域过大写不出完整 DAG | 停下，先出拆分方案 |
| 说明书过长 | 拆附录，主文档要能独立读完 |
